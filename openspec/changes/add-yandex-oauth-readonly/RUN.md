## Решения этапа 2

- **Сверх спеки: запрет `{n}` / `{n+}` в конце последнего аргумента.** Такой хвост заставляет сервер ждать литерал, и следующая команда (с непроверяемым литералом) рассинхронизируется. Добавлять литерал может только сам imaplib.
- **Любая ошибка внутри проверки = `ReadOnlyViolation`** (fail-closed): непредвиденный тип аргумента, не-ASCII в FETCH и т. п.
- **Сравнение имён команд и подкоманд `UID` — точное, в верхнем регистре.** imaplib сам переводит в верхний регистр; `uid("fetch")` проходит, прямой `_command("UID", "fetch")` отклоняется, чтобы FETCH нельзя было обойти мимо токенизатора.
- **Секция `BODY.PEEK[...]` без кавычек и литералов**: `HEADER.FIELDS ("FROM")` отклоняется. Нашему коду кавычки там не нужны.
- **Литерал** допускается `bytes`/`bytearray` у любой разрешённой команды, callable — только у `AUTHENTICATE`, другие типы — нарушение.
- **`ReadOnlyViolation(Exception)`, а не подкласс `imaplib.IMAP4.error`**, чтобы его не проглотили обработчики ошибок imaplib и imap-tools. Признак непригодности соединения — `client.broken`; пул этапа 4 должен его проверять.
- **`open_box(account, folder="INBOX")`**: вход и `EXAMINE` внутри `try`, так что `logout` выполняется и при ошибке выбора папки.
- **Различия imaplib по версиям** (учтены в фейковом сервере тестов): 3.13.16 берёт CAPABILITY из приветствия и перезапрашивает после `AUTHENTICATE`, оборачивает элементы `FETCH` в скобки, `uid()` сам отклоняет лишние аргументы; 3.14 читает через `sock.recv`, а не `makefile`.

## Решения этапа 3

- **3.1 закрыт замером (mcp 2.0.0 из `uv.lock`, реальный `MCPServer`, без сети):** `CallToolResult(isError=True)` из инструмента со схемой выхода (`-> TypedDict`, `-> list[dict]`) НЕ проходит мимо проверки: `convert_result` валидирует его `structured_content` (None) и отдаёт `ToolError` с текстом ошибки pydantic. У `-> dict` схемы нет, там проходит. Исключение `ToolError("… ***")` из инструмента клиент получает как `isError: true` с текстом `Error executing tool X: … ***`.
- **`@safe_tool` бросает `ToolError(redact(...)) from None`, а не возвращает `CallToolResult`** (выбор пользователя 2026-10-10). Запасной вариант D15 «объект по схеме с `errors`» отвергнут: теряет `isError: true`, которого требует сценарий спеки. Текст требования и D15 поправлены под этот механизм.
- **Фикстуры ответов Яндекса** собраны по перечню полей из документации (screen-code-oauth, token-invalidate): WebFetch отдаёт пересказ, дословный текст получить не удалось. Сверить с живым обменом в 6.2 (`auth --trace`).
- **Из документации (до живой проверки 6.2):** `client_secret` в запросе токена необязателен (профиль: `client_secret_required=False`); поле `scope` в ответе появляется, только если права урезаны; `/revoke_token` отвечает `{"status": "ok"}` даже для недействительного токена, а для токена без `device_id` — `unsupported_token_type`. Ручной отзыв: https://id.yandex.ru/personal/data-access.
- **Форма XOAUTH2 по умолчанию двухшаговая** (`imaplib.authenticate` через `imap-tools`); однострочная включается флагом профиля `xoauth2_inline` после 6.2.
- **`client_secret` спрашивается только при `client_secret_required`.** У Яндекса он не нужен, поэтому `forget` по умолчанию не отзывает токен, а печатает ссылку на ручной отзыв. Если 6.2 покажет, что секрет нужен, — переключить флаг профиля.
- **Реестр секретов в `redact.py` глобальный:** всё, что процесс прочитал (пароль, токены, `client_secret`, `device_code`, строка XOAUTH2), заменяется дословно; вдобавок шаблоны `Bearer`, полей `access_token`/`refresh_token`/`client_secret`/`device_code`/`password` и base64, внутри которого `auth=Bearer`. Значения короче 6 символов не регистрируются, иначе маскировались бы обычные слова.
- **Статус `unreachable`** пишется как `unreachable: <тип> (<host>:<port>)` — спека требует хост и порт в тексте.
- **Повреждённая запись в keyring** — `CorruptRecord`; `forget` её всё равно удаляет.
- **Тесты не трогают системное хранилище:** autouse-фикстура ставит keyring в памяти. Фейковый IMAP-сервер вынесен в `tests/fakeimap.py`, фикстура `sockets` — в `conftest.py`.

## Решения этапа 4

- **Целые параметры (`limit`, `offset`, `max_chars`) объявлены как `IntArg = Annotated[Any, WithJsonSchema({"type": "integer"})]`.** Замер на mcp 2.0.0: при `limit: int` вызов `limit="много"` даёт `isError` с текстом валидации pydantic, а сценарий спеки требует свой текст про `limit`. Схема для модели остаётся `integer`, проверяет `validate.py`.
- **`list_folders(account?)`:** `account` необязателен, без него — все включённые аккаунты, как у других списков. У спеки сигнатура `list_folders(account)`; форма `{rows, errors}` под несколько аккаунтов это допускает.
- **`search_emails` получил `folder` и `unread_only`:** спека называет `unread_only` общим критерием поиска, у upstream его не было.
- **Неизвестный, выключенный или битый аккаунт в `account=` — запись в `errors`, а не `isError`** (4.12: разрешение аккаунтов внутри обработки ошибок). Текст начинается с `account:` и перечисляет известные ключи. Неверный формат ключа — `isError` от `validate.py`; недоступный конфиг — `isError`.
- **Тексты ошибок аккаунта:** `TimeoutError` → `unreachable: timeout`; обрыв (`OSError`, `imaplib.IMAP4.abort`) → `unreachable: <тип> (host:port)`; нет учётных данных → `<статус>: <подсказка>`; ожидаемые отказы (`MailError`, `ArgumentError`) — текстом как есть; остальное — `<тип>: <текст>`. Всё через `redact`.
- **Дедлайн 45 с — хук `before_command` в охраннике:** вызывается после проверки команды и до отправки, ставит тайм-аут сокета `min(30, остаток)`, а при истечении бросает `TimeoutError` и закрывает соединение. Ошибка после истечения дедлайна тоже считается тайм-аутом.
- **Пул:** одно переподключение на вызов при обрыве (кроме `TimeoutError`); устаревшее соединение (упал `NOOP`) заменяется без учёта этой попытки. После NO/BAD и наших `MailError`/`ArgumentError` соединение остаётся в пуле, после прочих ошибок закрывается. Простой: проверка при захвате и фоновый поток-уборщик (`sweep` с неблокирующим захватом, раз в 30 с).
- **Бюджет 45 000 символов** меряется тем же сериализатором, что у mcp для текста результата (`pydantic_core.to_json(..., indent=2)`), число строк подбирается бинарным поиском.
- **Второй проход** идёт по `RFC822.SIZE` от больших UID к меньшим и останавливается на первом письме, которое не помещается в 3 МБ («пока не превысит»). Письмо без `RFC822.SIZE` сниппета не получает.
- **`attachments` в `get_email` этапа 4 — без `extractable` и `reason`:** их добавит задача 5.1 вместе с определением типа по сигнатуре.
- **Псевдонимы special-use берутся из флагов обычного `LIST`**, без `LIST ... RETURN (SPECIAL-USE)`. Отдаёт ли их так Яндекс — открытый вопрос (6.5).
- **Раздел README «Tools» обновлён в этом этапе**, потому что интерфейс инструментов поменялся; остальная документация — этап 6.
- **Тесты на фейковом сервере с ящиком** (`tests/fakemail.py`): LIST, STATUS, EXAMINE, UID SEARCH с литералами, UID FETCH, фейковые часы и задержка ответа, которая упирается в тайм-аут сокета. Фикстура `mail` подменяет `server.pool` на пул с фейковыми часами.

## Решения этапа 5

- **`imap_mcp/__init__.py` импортирует `cli` лениво, внутри `main()`.** Замер: `import imap_mcp` тянул `imap_tools` и `imaplib` через `cli` → `accounts`, а дочерний процесс импортирует пакет ради `_extract_worker`. Тест `test_worker_does_not_import_server_mcp_or_imap` проверяет `sys.modules` ребёнка.
- **Сигналом «начинай» служит само задание:** родитель запускает процесс, назначает Job Object и только потом шлёт `{kind, data}` через `Pipe`; до получения ребёнок ничего не разбирает.
- **`join(30)` из D12 — это `join` вспомогательного потока, который отправляет задание и читает ответ** (после ревью, тред 4299336913; сначала было `poll` + `recv`). Голый `join` процесса зависнет, если ребёнок блокирован на отправке длинного текста; `send` 15 МБ блокируется, пока ребёнок не прочтёт. По сроку — `kill()`, поток завершается на оборванном канале. Срок считается от `start()`.
- **`memory limit` — из `MemoryError` в ребёнке** (Job Object и `RLIMIT_AS` дают отказ в выделении, а не убийство). Ребёнок, умерший без ответа, — `parse error: процесс разбора завершился с кодом N`. Порт завершения Job Object для распознавания не делали.
- **Job Object с `KILL_ON_JOB_CLOSE`:** если сервер умрёт, Windows закроет дескриптор задания и убьёт разбор. Процесс назначается по `proc.sentinel` (документированный дескриптор процесса); multiprocessing в venv запускает базовый интерпретатор, а не лаунчер, — тест памяти это подтверждает.
- **TXT/CSV декодируются в родителе**, без процесса: спека требует изоляции только для PDF и DOCX, у декодирования нет разборщика. Функции `decode_text`/`bom` живут в `_extract_worker.py` вместе с остальными разборщиками.
- **DOCX в родителе определяется по `PK\x03\x04` и имени `word/document.xml` в байтах**, без разбора ZIP в процессе сервера; исполнитель открывает архив `zipfile` и проверяет сам. ZIP с `xl/workbook.xml` называется XLSX, остальное — `application/zip`.
- **`type mismatch` — только для найденных сигнатур PDF и DOCX** и конкретного заявленного типа вне списка согласующихся (`application/pdf`, `x-pdf`, `acrobat`; для DOCX ещё `msword`, `zip`, `x-zip-compressed`). Другие сигнатуры (PNG, JPEG, OLE и т. п.) — `unsupported type`. У текста сигнатуры нет, поэтому CSV как `application/vnd.ms-excel` с именем `.csv` несовпадением не считается.
- **Порядок причин `extractable: false`:** `type mismatch` / `unsupported type`, потом `too large`. В `reason` метаданных — только ключевое слово, подробности — в ошибке `get_attachment_text`.
- **Кэш:** `get_email` всегда ходит на сервер (свежие флаги) и кладёт письмо в кэш; `get_attachment_text` берёт из кэша. Порядок вытеснения — по времени скачивания, `get` срок не продлевает. Аккаунт из id проверяется и при попадании в кэш.
- **Фикстуры строятся в тестах** (`tests/docfixtures.py`): PDF через `pypdf` (текст Helvetica, страница-скан с картинкой, AES-128), DOCX вручную. ZIP-бомба 2 ГБ → 2 МБ собирается за ~1,3 с из повторённого deflate-блока после `Z_FULL_FLUSH` (через `zipfile` — 12 с).
- **Тестовые исполнители** (`tests/workers.py`) — настоящий `serve()` с подменённым обработчиком: сон, выделение памяти, печать, список модулей, `os._exit(3)`.
- **Замер вне тестов:** родитель с stdout/stderr-пайпами (как MCP на stdio) запускает шумный исполнитель — в пайп пришла только строка родителя.

## Принятые решения (не пересматривать без нового повода)

- **Основа — upstream imap-mcp, а не свой сервер с нуля.** Причина: маленький, MIT, уже read-only по коду.
- **Мультиаккаунт.** Позже будут Gmail и другие; для read-only Gmail нужен отдельный бэкенд на Gmail API.
- **Вложения:** метаданные + текст из PDF/DOCX/TXT.
- **Ящики Яндекса:** и личные, и в Яндекс 360. В инструкцию входит раздел про администратора организации.
- **Токен обновляется вручную раз в год, автообновления нет** (REVIEW-2 №5, вариант Б). Причина: Яндекс часто возвращает прежний токен, а автообновление — это примерно половина этапа 3. Refresh-токен сохраняется на будущее.
- **Рабочее место Claude Code только читает почту:** без `Write` и `Read`, режим `dontAsk`, в allow — только `mcp__imap-mcp__*`.
- **Ревью спеки:** все рекомендованные варианты REVIEW-1 и REVIEW-2 приняты, кроме REVIEW-2 №5 (см. выше).
- **Технические развилки REVIEW-2:**
  - кириллический поиск — три `UID SEARCH` с литералом;
  - ответ списков — объект `{rows, errors, …}`;
  - аккаунт хранится внутри id;
  - `device_id` передаётся при авторизации.
- **Пакет и точка входа:** остаются `imap_mcp` / `imap-mcp`, чтобы проще сливать с upstream.
- **Процесс /feature-run (согласовано 2026-10-09):**
  - этапы как в `tasks.md`, 3 и 4 не делим: пользователь осознанно принял MR на 2,5–3 тыс. строк;
  - ветки: подветка `stage/N-<суть>` от `main`, PR в `main`, общей ветки фичи нет;
  - `uv` ставится через `winget install --id astral-sh.uv -e`;
  - цикл замечаний ревью: раз в 20 минут, не больше 4 кругов.

## Грабли

- **`gh pr create` в форке** по умолчанию целится в upstream и падает с «No commits between». Сделано `gh repo set-default MaxRyabov/EMailMcp`, но надёжнее явно передавать `--repo MaxRyabov/EMailMcp`.

- **`openspec validate --strict`** требует SHALL или MUST в первом абзаце требования, перед списками. Русский текст без этих слов валидацию не проходит.
- **Бот codebear:**
  - в GitHub выкладывает только часть замечаний: в сводке PR #1 было 22, в тредах 8, остальные лежат на codebear.itexpert.ru, куда у Claude нет доступа;
  - каждый прогон комментирует сгенерированные файлы `.claude/`; исключить путь в его настройках пока не удалось.
- **Bash-heredoc на этой машине портит обратную косую черту:** в `python - <<'EOF'` строки `"\r\n"` и `"\\0"` превращались в настоящий перевод строки, файлы ломались (этап 3, трижды). Многострочные правки с `\` — только скриптом, записанным через Write, и `python -I script.py`.
- **Инструмент Write раскрывает `\uXXXX` в содержимом в настоящий символ** (этап 5: `"﻿…"` в тесте стал невидимым BOM). `\xNN` и `\n` остаются текстом. Невидимые символы в Python-коде — через `chr(0x…)` или байты, после записи проверять скриптом на категории `Cf`.
- **`gh api .../pulls/N/comments` без `--paginate` отдаёт только 30 тредов** (у PR #4 их было 38).
- **codebear перепроверяет каждый пуш** и выдаёт новую порцию LOW-замечаний; запускается с задержкой в часы — на PR #4 все 4 круга cron прошли пустыми, ревью пришло после. Новые треды искать сравнением с прошлой выгрузкой (`pr4_c*.json` в scratchpad).
- **WebFetch пересказывает страницы** документации Яндекса, а не цитирует: фикстуры ответов собраны по перечню полей.
- **Не удалось проверить через WebFetch:** lobehub отдаёт 403. Часть фактов о mcp 2.0.0 ревьюеры смотрели по ветке main, а не по тегу; это проверяет задача 3.1.
