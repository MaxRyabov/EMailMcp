# Ревью спеки №2 (spec-review, повторный прогон, 2026-10-09)

## Итог

Блокирующих замечаний нет, в реализацию идти можно. Но №1–3 меняют контракт инструментов, их лучше закрыть до этапа 4, иначе переделывать придётся вместе с тестами. Всего 20 замечаний: блокирует реализацию — 0, стоит поправить — 11, на подумать — 9; ещё 5 в «Что пропущено» (№21–25). Из 36 замечаний REVIEW-1 закрыто 29, частично 7, не закрытых нет.

Самое дорогое — **№1**: поиск по кириллице литералом в описанном виде не реализуется. `imaplib` добавляет к команде только один литерал, и только в конец, а запрос upstream содержит строку трижды (FROM, SUBJECT, TEXT). Обходной путь через callable-литерал отправляет текст команды мимо проверки CR/LF в охраннике.

## Что пропущено

21. **`device_id` не передаётся в device flow.** По документации Яндекса `/revoke_token` отзывает только токены, выданные с `device_id`, и требует `client_secret`. Без этого `forget` может лишь удалить локальную запись, а каждый повторный `auth` оставляет предыдущий токен активным в Яндекс ID. Лимит — 30 токенов на устройства для одного пользователя и приложения. Стоит передавать стабильный `device_id` (например, хэш машины и аккаунта) и `device_name`, а `forget` должен отзывать токен, если есть `client_secret`.
22. **Порядок блокировок.** И пул (D13), и refresh (D5) держат «lock аккаунта». Если это один `threading.Lock`, первый же вход из пула, вызывающий refresh, зависнет навсегда (Lock не реентерабельный). Нужно назвать две разные блокировки и порядок их захвата.
23. **Память процесса разбора.** R11 отмечал, что лимита памяти нет; переработка добавила `kill()` по времени, но не по памяти. За 30 с декомпрессия может занять гигабайты. Варианты: Job Object с лимитом памяти на Windows или проверка RSS из родителя.
24. **stdout дочернего процесса.** На Linux при `spawn` дескрипторы наследуются, и случайный `print` в дочернем процессе испортит поток MCP на stdio (предположение; на Windows зависит от наследования хендлов). В исполнителе стоит перенаправить stdout в `devnull`. Сюда же: при `spawn` дочерний процесс заново импортирует `imap_mcp`, а значит `server.py` и `mcp`; исполнитель лучше держать в модуле без тяжёлых импортов.
25. **Верхняя граница скачивания в `get_email`.** Письмо скачивается целиком ради тела и метаданных вложений, ограничения нет. Кэш отсекает только письма больше 25 МБ. Нужен порог (например, 40 МБ), выше которого `get_email` отдаёт заголовки и `BODYSTRUCTURE` без тела.
