## ADDED Requirements

### Requirement: Способ входа задаётся для каждого аккаунта
Каждый аккаунт в `accounts.toml` SHALL иметь способ входа `auth` со значением `password` или `oauth`. Если поле не указано, SHALL применяться `password`, и конфиги upstream работают без правок.

Требования к полям:
- `key` MUST соответствовать `^[a-z0-9_-]{1,32}$`, так как входит в идентификатор письма;
- для `oauth` поле `oauth_provider` MUST быть указано и MUST совпадать с зарегистрированным провайдером (в этой версии только `yandex`), а поле `client_id` MUST быть указано;
- для `password` поле `password_env` MUST быть указано;
- ключ `scope` в описании аккаунта MUST отклоняться: права задаёт только профиль провайдера.

#### Scenario: Конфиг upstream без поля auth
- **WHEN** аккаунт описан только полями upstream (`key`, `email`, `host`, `password_env`)
- **THEN** аккаунт загружается со способом входа `password` и ведёт себя как в upstream

#### Scenario: OAuth-аккаунт без провайдера
- **WHEN** у аккаунта `auth = "oauth"`, а `oauth_provider` отсутствует
- **THEN** аккаунт получает статус `config-error` с ключом аккаунта и именем поля `oauth_provider`

#### Scenario: Неизвестный провайдер
- **WHEN** у аккаунта `oauth_provider = "gmail"`, а такой провайдер не зарегистрирован
- **THEN** аккаунт получает статус `config-error` со списком поддерживаемых провайдеров

#### Scenario: Попытка расширить права через конфиг
- **WHEN** в описании аккаунта указан ключ `scope`
- **THEN** аккаунт получает статус `config-error` с пояснением, что права задаются только профилем провайдера

#### Scenario: Недопустимый ключ аккаунта
- **WHEN** `key = "Мой ящик"`
- **THEN** аккаунт получает статус `config-error` с допустимым форматом ключа

### Requirement: Ошибка в одном аккаунте не выводит из строя остальные
Конфиг SHALL разбираться по аккаунтам. Аккаунт с ошибкой описания SHALL получать статус `config-error: <причина>` и SHALL исключаться из обращений к почте; остальные аккаунты SHALL работать. Если файл конфига отсутствует или не разбирается как TOML, все инструменты SHALL возвращать понятную ошибку с путём к файлу, и процесс сервера MUST NOT завершаться. Сервер SHALL перечитывать `accounts.toml` при изменении mtime файла, без перезапуска. Повторяющийся `key` SHALL давать `config-error` обоим аккаунтам.

#### Scenario: Опечатка в одном из двух аккаунтов
- **WHEN** у второго аккаунта нет поля `host`, а первый описан верно
- **THEN** `list_accounts` показывает первый со статусом `ok`, второй — `config-error: missing host`; `list_emails()` возвращает письма первого и ошибку второго

#### Scenario: Правка конфига при работающем сервере
- **WHEN** пользователь добавил аккаунт в `accounts.toml`, не перезапуская Claude Code
- **THEN** следующий вызов `list_accounts` показывает новый аккаунт

### Requirement: Профиль провайдера описывает протокол
OAuth-провайдер SHALL описываться профилем `ProviderProfile`:
- URL запроса device code;
- URL токена;
- URL отзыва токена;
- обязательный scope;
- IMAP-хост и порт по умолчанию;
- значение `grant_type` для device code;
- имя параметра, в котором передаётся device code;
- имя поля verification URL в ответе;
- коды ошибок, при которых опрос продолжается, и фатальные коды с текстами для пользователя;
- нужен ли `client_secret`;
- `expiry_warning` — за сколько до истечения предупреждать.

Профиль `yandex` SHALL содержать значения из документации Яндекса:

| Поле профиля | Значение |
|---|---|
| URL запроса device code | `https://oauth.yandex.ru/device/code` |
| URL токена | `https://oauth.yandex.ru/token` |
| URL отзыва токена | `https://oauth.yandex.ru/revoke_token` |
| scope | `mail:imap_ro` |
| IMAP-хост и порт | `imap.yandex.com:993` |
| `grant_type` | `device_code` |
| параметр с device code | `code` |
| поле verification URL | `verification_url` |
| ошибки, при которых опрос продолжается | `authorization_pending`; `slow_down` — с увеличением интервала на 5 секунд (RFC 8628 §3.5) |
| фатальные ошибки | `invalid_grant`, `invalid_client`, `invalid_request`, `invalid_scope`, `unauthorized_client`, `unsupported_grant_type`, `bad_verification_code`, `access_denied`, `expired_token` |
| `client_secret` | необязателен |
| `expiry_warning` | 30 дней |

#### Scenario: Хост по умолчанию для Яндекса
- **WHEN** у OAuth-аккаунта с `oauth_provider = "yandex"` не указан `host`
- **THEN** используется `imap.yandex.com`, порт `993`

#### Scenario: Запрос токена по device code к Яндексу
- **WHEN** клиент запрашивает токен по полученному device code
- **THEN** тело POST-запроса содержит `grant_type=device_code` и `code=<device_code>`, а не имена из RFC 8628

### Requirement: Получение токена через device flow
Команда `imap-mcp auth <account>` SHALL получать токен для OAuth-аккаунта:
1. запросить device code с `client_id`, scope профиля, стабильным `device_id` (хэш имени машины и ключа аккаунта, 6–50 печатаемых ASCII-символов) и `device_name` (`imap-mcp <account> on <имя машины>`);
2. вывести `user_code` и verification URL;
3. опрашивать URL токена не чаще `interval`, пока не получен токен, не истёк `expires_in` пары кодов или не пришла фатальная ошибка;
4. проверить права в ответе;
5. выполнить пробный вход в IMAP с новым токеном;
6. только после успешного входа сохранить токен, refresh-токен и срок действия.

Если в ответе есть поле `scope`, отличное от запрошенного, команда MUST NOT сохранять токен. Для аккаунта с `auth = "password"` команда SHALL завершаться ошибкой без сетевых запросов. Ctrl+C во время опроса SHALL завершать команду с кодом 130 без записи в хранилище.

Каждый HTTP-запрос SHALL выполняться с тайм-аутом 15 секунд. Ошибки SHALL классифицироваться так:
- ответ 4xx с JSON-полем `error` — по таблице кодов профиля; код, которого нет ни среди продолжающих опрос, ни среди фатальных, SHALL считаться фатальным с текстом «неизвестный ответ провайдера: <код>» (плюс `error_description`, если есть);
- тайм-аут, ошибка соединения, ответ 5xx, ответ без JSON — сетевая ошибка с хостом и типом.

`urllib.error.HTTPError` MUST разбираться раньше `URLError`.

Флаг `--trace` SHALL печатать в stderr обмен HTTP и IMAP (команды и ответы) после редактирования секретов. Так видно, например, однострочную или двухшаговую форму `AUTHENTICATE`.

#### Scenario: Успешная авторизация
- **WHEN** пользователь запускает `imap-mcp auth yandex`, вводит код на странице провайдера, и пробный вход в IMAP проходит
- **THEN** команда сохраняет токены, печатает «авторизация выполнена», дату истечения токена и результат входа в IMAP и завершается с кодом 0

#### Scenario: Токен получен, а IMAP отказывает
- **WHEN** токен получен, а пробный вход `AUTHENTICATE XOAUTH2` отклонён
- **THEN** команда не сохраняет токен и печатает вероятные причины:
  - в настройках почты выключен «IMAP с OAuth-токенами» (путь «Все настройки → Почтовые программы»);
  - для ящика Яндекс 360 администратор организации запретил IMAP или сторонние приложения.

  Код возврата ненулевой

#### Scenario: Пользователь не ввёл код вовремя
- **WHEN** срок `expires_in` пары кодов истёк, а токен не получен
- **THEN** команда печатает, что код истёк и авторизацию нужно запустить заново, ничего не сохраняет и завершается с ненулевым кодом

#### Scenario: Ожидание ввода кода
- **WHEN** провайдер отвечает `authorization_pending`
- **THEN** команда продолжает опрос с интервалом не меньше `interval` из ответа на запрос device code

#### Scenario: Фатальные ошибки провайдера
- **WHEN** провайдер отвечает одной из фатальных ошибок
- **THEN** команда печатает объяснение для конкретного кода, не печатая секретов, и не сохраняет токен:
  - `invalid_client` — неверный `client_id` или `client_secret`, где они настраиваются;
  - `unauthorized_client` — приложение на модерации или заблокировано;
  - `invalid_scope` — права приложения изменились, нужно проверить, что выбрано только чтение писем;
  - `invalid_grant` / `bad_verification_code` / `expired_token` — код неверен или просрочен, авторизацию нужно запустить заново;
  - `access_denied` — пользователь отказал в доступе на странице подтверждения

#### Scenario: Пользователь отказал в доступе
- **WHEN** на странице подтверждения пользователь нажал «Отказать», и провайдер ответил `access_denied`
- **THEN** команда печатает «доступ не предоставлен, токен не получен», ничего не сохраняет и завершается с ненулевым кодом

#### Scenario: Провайдер просит опрашивать реже
- **WHEN** провайдер отвечает `slow_down`
- **THEN** интервал опроса увеличивается на 5 секунд и опрос продолжается

#### Scenario: Неизвестный код ошибки
- **WHEN** провайдер отвечает кодом, которого нет в таблицах профиля
- **THEN** опрос прекращается, команда печатает «неизвестный ответ провайдера: <код>» и `error_description`, ничего не сохраняет и завершается с ненулевым кодом

#### Scenario: Выдан неполный набор прав
- **WHEN** ответ с токеном содержит поле `scope`, не совпадающее с `mail:imap_ro`
- **THEN** команда сообщает, какие права выданы, токен не сохраняет и завершается с ненулевым кодом

#### Scenario: Нет сети или сервер завис
- **WHEN** `oauth.yandex.ru` недоступен или не отвечает 15 секунд
- **THEN** команда печатает хост и тип сетевой ошибки и завершается с ненулевым кодом без записи в хранилище

### Requirement: Хранение секретов вне файлов проекта
OAuth-токены (access и refresh), время их истечения, время получения и `client_secret` SHALL храниться в системном хранилище через `keyring` под сервисом `imap-mcp` и ключом аккаунта. Они MUST NOT записываться в `accounts.toml`, файлы проекта, логи или stdout сервера.

На Windows записи SHALL создаваться с `CRED_PERSIST_LOCAL_MACHINE` (`keyring.get_keyring().persist = "local_machine"` у `WinVaultKeyring`), чтобы не перемещаться с профилем домена. Длина JSON-записи SHALL проверяться до записи по лимиту Credential Manager — 1280 символов UTF-16.

`client_id` не секретен и хранится в `accounts.toml`. Если провайдер требует `client_secret`, `imap-mcp auth` SHALL запрашивать его скрытым вводом при первом запуске.

Refresh-токен сохраняется для будущего автообновления, но в этой версии не используется.

#### Scenario: Повторная авторизация того же аккаунта
- **WHEN** для аккаунта уже есть сохранённые токены и пользователь снова запускает `imap-mcp auth`
- **THEN** после успешного получения и пробного входа новые токены заменяют старые, при неудаче старые остаются нетронутыми

#### Scenario: Хранилище секретов недоступно
- **WHEN** `keyring` не может открыть системное хранилище
- **THEN** `imap-mcp auth` завершается ошибкой с именем бэкенда keyring, без попытки сохранить токен в файл

#### Scenario: Запись слишком длинная
- **WHEN** JSON-запись длиннее 1280 символов
- **THEN** команда завершается ошибкой с фактической длиной и лимитом, частичная запись не выполняется

### Requirement: Срок действия токена и повторная авторизация вручную
Сервер MUST NOT обновлять токены автоматически: повторная авторизация выполняется вручную командой `imap-mcp auth`.

Если до истечения токена меньше `expiry_warning` профиля, статус SHALL оставаться `ok`, но `list_accounts` и `imap-mcp status` SHALL показывать предупреждение с датой истечения и командой `imap-mcp auth <account>`. После истечения аккаунт SHALL получать статус `reauth-required` без обращения к IMAP.

Если вход `AUTHENTICATE XOAUTH2` отклонён при действующем по сроку токене, аккаунт SHALL получать статус `reauth-required`, а сообщение SHALL перечислять обе причины: доступ приложения отозван в Яндекс ID; выключен «IMAP с OAuth-токенами» или его запретил администратор Яндекс 360.

Сервер SHALL читать токены из хранилища при каждом входе: токен, полученный через `imap-mcp auth`, действует без перезапуска.

#### Scenario: Токен скоро истекает
- **WHEN** до истечения токена осталось 20 дней
- **THEN** статус `ok`, в `list_accounts` есть предупреждение с датой и командой `imap-mcp auth yandex`, почта читается

#### Scenario: Токен истёк
- **WHEN** срок токена истёк
- **THEN** статус `reauth-required` с командой `imap-mcp auth <account>`, IMAP-вход не выполняется, другие аккаунты отвечают

#### Scenario: Отказ входа при действующем токене
- **WHEN** токен действителен по сроку, а `AUTHENTICATE XOAUTH2` отклонён
- **THEN** статус `reauth-required`, сообщение перечисляет обе причины

#### Scenario: Выход из reauth-required
- **WHEN** пользователь выполнил `imap-mcp auth` при работающем сервере
- **THEN** следующий вызов `list_accounts` показывает `ok` без перезапуска сервера

### Requirement: Удаление токенов
Команда `imap-mcp forget <account>` SHALL:
1. отозвать токен у провайдера через URL отзыва профиля, если сохранён `client_secret` (у Яндекса отзыв работает только для токенов, выданных с `device_id`, и требует `client_secret`);
2. удалить из хранилища токены и `client_secret` аккаунта;
3. напечатать результат отзыва и где отозвать доступ вручную (раздел управления доступами в Яндекс ID), если программный отзыв невозможен или не удался.

Повторный вызов без сохранённых данных SHALL завершаться с кодом 0 и сообщением «нечего удалять».

#### Scenario: Отключение аккаунта с client_secret
- **WHEN** пользователь выполняет `imap-mcp forget yandex`, и `client_secret` сохранён
- **THEN** токен отозван у Яндекса, записей `imap-mcp` для аккаунта в Credential Manager нет, `imap-mcp status` показывает `no-credential`

#### Scenario: Отключение аккаунта без client_secret
- **WHEN** `client_secret` не сохранён
- **THEN** локальные записи удалены, команда печатает, что токен на стороне Яндекса остаётся активным до отзыва вручную, и где это сделать

### Requirement: Статусы аккаунтов
Статус SHALL вычисляться при каждом вызове и MUST NOT кэшироваться между вызовами. `list_accounts` и `imap-mcp status` SHALL выполнять реальный вход в IMAP (через пул соединений), и `ok` SHALL означать «вход выполнен сейчас».

Возможные статусы:
- `ok`;
- `disabled`;
- `no-credential` (нет пароля в окружении или токенов в хранилище);
- `reauth-required`;
- `config-error: <причина>`;
- `unreachable: <тип ошибки>`.

Без входа в IMAP определяются только `disabled`, `config-error`, `no-credential` и `reauth-required` по истёкшему сроку. Команда `imap-mcp status --offline` SHALL показывать только их и не обращаться к сети.

Для OAuth-аккаунта SHALL дополнительно возвращаться дата истечения токена (без самого токена) и предупреждение по требованию о сроке действия. Если включённых аккаунтов нет, `list_accounts` SHALL сообщать об этом и называть путь к конфигу.

#### Scenario: OAuth-аккаунт ещё не авторизован
- **WHEN** у OAuth-аккаунта нет токенов в хранилище
- **THEN** `list_accounts` возвращает статус `no-credential` и подсказку `imap-mcp auth <account>` без сетевых запросов

#### Scenario: Проверка без сети
- **WHEN** пользователь выполняет `imap-mcp status --offline`
- **THEN** печатаются статусы, определяемые без входа, у остальных аккаунтов — `not checked`, сетевых соединений нет

#### Scenario: Сервер недоступен по сети
- **WHEN** TCP-соединение с IMAP-хостом не устанавливается
- **THEN** статус `unreachable: <тип ошибки>` с хостом и портом в тексте

### Requirement: Секреты не попадают в выдачу инструментов
Каждый инструмент SHALL быть обёрнут декоратором `@safe_tool`. Декоратор перехватывает любое исключение и бросает вместо него `ToolError` с отредактированным текстом, без цепочки исходного исключения; клиент получает результат с `isError: true` и этим текстом. Возврат `CallToolResult(isError=True)` не используется: mcp 2.0.0 проверяет его по схеме выходных данных инструмента (задача 3.1).

Любой текст, который сервер возвращает клиенту или пишет в stderr, SHALL проходить редактирование: access- и refresh-токены, пароль, `client_secret` и base64-строка XOAUTH2 MUST заменяться на `***`. Сообщения CLI и вывод `--trace` SHALL проходить то же редактирование.

#### Scenario: Исключение содержит токен
- **WHEN** исключение из IMAP- или HTTP-слоя содержит access-токен или его XOAUTH2-кодировку
- **THEN** текст ошибки в ответе инструмента содержит `***`, исходного значения в ответе нет

#### Scenario: Необработанное исключение в любом инструменте
- **WHEN** любой зарегистрированный инструмент выбрасывает исключение с секретом в тексте
- **THEN** клиент получает результат с `isError: true` и отредактированным текстом, а не ошибку валидации схемы или `ToolError` с исходным текстом

#### Scenario: Трассировка авторизации
- **WHEN** пользователь запускает `imap-mcp auth yandex --trace`
- **THEN** в stderr видны команды IMAP и HTTP-запросы, вместо токенов, `client_secret` и строки XOAUTH2 — `***`
